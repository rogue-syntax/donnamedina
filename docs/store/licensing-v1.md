# Licensing v1: signed license tokens

**Status:** backend built 2026-11-20 (see 3.2); plugin side not built yet. Spec 2026-11-19, revised 2026-11-20: one token format for every Rogue-Syntax plugin, `RS1.` prefix; buyer's name required at sign-up).

**Audience:** every Rogue Syntax plugin developer, and whoever works on the store (`/var/www/rogue-syntax`, Go). Section 1 is the shared contract and both sides must follow it exactly. Section 2 covers the plugin, Section 3 the store. **Plugin developers: start with `PLUGIN-DEVELOPER-CHECKLIST.md` in the installer recipe.**

**How it works:** public-key signatures.

- The **backend** holds a private key and signs one license per customer.
- The **plugin** contains only the public key, so it can check a license but can never create one.
- Every customer gets the **same plugin binary**. Nothing is injected into the binary per customer.

## 1. Shared contract (both sides)

### 1.1 Algorithm
Ed25519 (RFC 8032), with a 64-byte signature and a 32-byte public key.

- **Backend:** Go `crypto/ed25519`.
- **Plugin:** any standard Ed25519 verifier (SHA-512, as in RFC 8032). Variants built on another hash don't verify these signatures (for example Monocypher's default `crypto_eddsa_*`, which uses BLAKE2b; its `crypto_ed25519_*` is the standard one).

### 1.2 Payload
UTF-8 text with one `key=value` per line. Every line, including the last, ends in `\n` (LF only).

- The backend writes the keys in this order. The plugin must not depend on the order.
- Split each line on the **first** `=`, because values may contain `=`.

| key | value | notes |
|---|---|---|
| `v` | `1` | Format version. The plugin rejects any other value. |
| `product` | Product ID, e.g. `testplugin` | Lowercase `[a-z0-9]{1,32}`. Each plugin knows its own ID and rejects any other value. The ID never changes once a plugin ships; the backend keeps the list (one per row of the products table). |
| `kid` | Integer, e.g. `1` | Which signing key signed this license (see 1.5). `0` is the TEST key and is never used in production. |
| `lid` | e.g. `TEST-000123` | License ID, unique across all products, generated by the backend (a short product prefix plus the store's licence number). Must match `[A-Za-z0-9-]{1,40}`. |
| `kind` | `full`, `dev` or `nfr` | `full` = customer, `dev` = the developer's own machines, `nfr` = press or demo copy. In v1 all three unlock the plugin. |
| `name` | Buyer's name | Shown in the plugin's About window. Always present and non-empty: the store requires a name at sign-up (max 50 characters, not unique). Max 80 bytes in the payload; the backend cuts longer names at a UTF-8 character boundary and strips CR, LF and control characters. |
| `email` | Buyer's email | Shown in the About window. Max 120 bytes, same stripping. |
| `issued` | `YYYY-MM-DD` | Date issued (UTC). |

- The whole payload is at most 1024 bytes.
- The backend may add new keys later. The plugin **ignores keys it does not know**, but they are still covered by the signature.

### 1.3 Token (what the customer receives)
```
RS1.<base64url(payload)>.<base64url(signature)>
```
- **One format for every Rogue-Syntax plugin.** `RS1` is the format, not the product; the payload's `product` key says which plugin the license is for. All plugins share the same signing keys (1.5). The prefix is not signed; it only identifies the format.
- **base64url:** RFC 4648 §5 (`-` and `_`), **no padding**.
- **Signature input:** the signature covers the exact payload bytes. The plugin verifies the decoded bytes first and only then parses them. Neither side re-serialises the payload before verifying.
- **Pasted tokens:** the plugin removes **all whitespace** (spaces, tabs, CR, LF) before parsing, because email clients wrap long lines. The backend never puts whitespace inside a token.

### 1.4 Where the license lives on the customer's machine
- **Location:** registry value `HKCU\Software\Rogue-Syntax\Registrations\<PluginKey>`, name **`License`**, type `REG_SZ`, holding the token. `<PluginKey>` is the plugin's registry subkey (1.7); each plugin has its own.
  - Windows only. A future macOS build needs its own location defined here first; the token format is the same. HKCU needs no admin rights, so the plugin can write the value itself.
- **Who writes it:**
  - the plugin, when the user pastes a token (Section 2);
  - the installer: it reads `license.txt` from the folder it was run from (the first line starting `RS1.`) and writes the token **as the logged-in user**, not the elevated admin account. The installer is the same file for every customer; the token is never built into it (3.6). If there's no `license.txt`, it offers to paste the key, and the customer can skip.

### 1.5 Keys and key IDs
- **`kid=0`, the TEST key.** It is public and is only for these test vectors.
  - Seed: `000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f`
  - Public key: `03a107bff3ce10be1d70dd18e74bc09967e4d6309ba50d5f1ddc8664125531b8`
  - Release builds of the plugin must **not** accept `kid=0`. Debug builds and tests may.
- **`kid=1`, the first production key.** The backend generates it (3.1). Only its **public** key is given to the plugin side.
- **Rotation:** the plugin holds a small table `kid -> public key`. Rotating means adding `kid=2` to the table in a plugin update and starting to sign with it. Old licenses keep working for as long as their `kid` stays in the table.

### 1.7 Plugin identity
Every identifier comes from the plugin's name, by the rules below. It **never changes once the plugin ships**, even if the plugin is renamed later: it's built into issued licences and customers' registries. The store works it out when the product is added, checks that nothing clashes, and sends it in `product.json` (1.9). Use the values in `product.json`.

First, remove accents (`ñ` → `n`, `ë` → `e`) and split the name into words on spaces and punctuation, keeping letters and digits.

| item | rule | example: "Example Plugin" | used in |
|---|---|---|---|
| Product ID | the words joined, lowercase (1–32 characters) | `exampleplugin` | `product` (1.2), the update check (1.8) |
| Registry subkey (`<PluginKey>`) | each word with its first letter capitalised, joined | `ExamplePlugin` | 1.4; the installer's `<PluginKey>Setup.exe` |
| Licence prefix | the first letter of each word, uppercase (one word: its first two letters; at most 3) | `EP` | licence IDs `<prefix>-<6 digits>` (1.2) |
| Shop page | `https://rogue-syntax.com/` + the words, lowercase, joined by `-` | `https://rogue-syntax.com/example-plugin` | the Buy button (2.3) |
| Installer ID (`AppGuid`) | UUID version 5, DNS namespace, name `<product ID>.plugins.rogue-syntax.com`, uppercase | `python -c "import uuid;print(str(uuid.uuid5(uuid.NAMESPACE_DNS,'exampleplugin.plugins.rogue-syntax.com')).upper())"` | the installer recipe |

If the prefix is already taken by another plugin, the store owner gives a different one.

### 1.8 Update check (every plugin)
Once a day the plugin tells the store which version it is and which licence it runs on. The store answers with the latest version. This also shows the owner how many computers each licence is used on.

**Request.** `POST https://rogue-syntax.com/v1/route_pluginCheck/`, body `application/x-www-form-urlencoded`, UTF-8:

| field | value |
|---|---|
| `product` | the plugin's product ID (1.7), e.g. `testplugin` |
| `version` | the plugin's version, digits and dots, up to 4 parts, e.g. `1.0.2` |
| `machine` | the computer ID, below: 64 lowercase hex characters |
| `licence` | the stored licence token (1.4), exactly as stored; **empty** when unregistered |

**Computer ID.** `machine` = lowercase hex SHA-256 of the UTF-8 bytes of `rogue-syntax:` + the Windows value `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid` (read it from the 64-bit registry view), as written (no case change). Every plugin computes it the same way, so one computer has one ID across all plugins. It can't be turned back into the GUID or the computer's name. If the value can't be read, skip the check.

**Authentication.** The licence token is the credential: the store verifies its signature and that it's for this product, and takes the licence ID from it. There's no other key or password; anything built into a plugin can be extracted, so it would add nothing. A missing or invalid token is counted as an unregistered copy. The check never changes whether the plugin is licensed: only the plugin's own check (Section 2) does that.

**Reply.** JSON. Use it only if HTTP 200 and `msg` is `"success"`:
```json
{"msg":"success", "route":"route_pluginCheck", "action":"nil", "displayMsg":"", "latest":"1.0.3", "update":true, "url":"https://rogue-syntax.com/"}
```
- `update` `true`: tell the customer, quietly:
  - a small **"Update available"** badge on the plugin's main screen; clicking it opens `url` in the browser;
  - the same line in the About window: "Update available: <latest>", with the link and a **"Hide until the next version"** option;
  - no pop-ups, nothing that blocks playing.
- **Hide:** store `<latest>` in the registry key from 1.4, value `SkipVersion` (`REG_SZ`). Don't show the badge while `latest` equals `SkipVersion`. A newer `latest` shows it again.
- **After updating:** the next check returns `update` `false` and the badge goes away. Keep the last answer (registry values `LatestVersion`, `UpdateURL`), so the badge shows between checks and offline; never show it once the plugin's own version is the same or newer.
- **`url`:** always use the one in the reply, never a built-in address. It's the store's home page for now and will become the customer's download page.
- Anything else (another `msg`, HTTP 429 or 5xx, bad JSON, no network, a timeout): do nothing and try again at the next check. Ignore unknown fields.

**Rules.**
- At most **once every 24 hours** per computer and plugin: keep the last check time in the registry key from 1.4, value `LastCheck` (`REG_SZ`, Unix seconds). Check when the plugin opens, if 24 hours have passed.
- **In the background, never on the audio thread**, with a 5-second timeout. The plugin must never wait for it or fail because of it.
- HTTPS only, with normal certificate checks (WinHTTP is fine).
- **Off switch:** a checkbox "Check for updates" in the About window, on by default. Off = registry value `UpdateCheck` = `0` (`REG_SZ`) in the same key, and no check is sent.
- Send nothing else: no name, email, IP-derived data or DAW details.

**Test it** with `curl`:
```
curl -d product=<your product ID> -d version=0.0.1 -d machine=$(printf 'rogue-syntax:test' | sha256sum | cut -c1-64) -d licence= https://rogue-syntax.com/v1/route_pluginCheck/
```

### 1.9 Release package (every release)
Each release goes to the store as one zip, built by the recipe's `build.ps1`. The store checks it before anything reaches customers.

**From the store: `product.json`** (in the plugin's developer pack):

| field | value |
|---|---|
| `brief` | `1` |
| `name`, `product_id`, `registry_key`, `licence_prefix`, `shop_page`, `app_guid` | the plugin's identity (1.7) |
| `store_product_no` | the store's product number |
| `installer_file` | `<registry_key>Setup.exe` |
| `newer_than` | the published version; the release must be newer (`""` = first release) |
| `pack_version` | the developer pack it came with |

**To the store: `<registry_key>-<version>.zip`**, holding exactly two files at its top level: `<registry_key>Setup.exe` and `manifest.json`:

| field | value |
|---|---|
| `manifest` | `1` |
| `name`, `product_id`, `registry_key`, `licence_prefix`, `shop_page`, `app_guid` | copied from `product.json` |
| `version` | the release, digits and dots, up to 4 parts; the same as the plugin's own version (1.8) |
| `installer_file`, `installer_sha256` | the installer's name and SHA-256 |
| `plugin_file`, `plugin_sha256` | the `.vst3` file or bundle folder's name, and its fingerprint (below) |
| `pack_version`, `recipe_sha256`, `eula_sha256` | the pack used: its `PACK_VERSION`, and fingerprints of `rogue-syntax.iss` and `eula.txt` |
| `git_commit` | the plugin's source commit, if known (for the record) |
| `built` | UTC time, e.g. `2026-11-20T17:00:00Z` |

Fingerprints are lowercase hex SHA-256. A text file's (`rogue-syntax.iss`, `eula.txt`) is taken with every CRLF read as LF. A bundle folder's is the SHA-256 of one line per file inside it, `<path relative to the bundle, / separators> <file's SHA-256>` plus a newline, sorted by byte value and joined.

**What the store checks on upload.** A failure rejects the package and changes nothing:
- the zip holds just those two files, and `manifest.json` is valid;
- the identity matches the store's record exactly, and the installer is named `<registry_key>Setup.exe`;
- the version is newer than the published one;
- the recipe is the current one (or one the store still accepts) and the EULA is the current one;
- the installer's SHA-256 matches the manifest;
- the installer's version info says `<name>™` and `<version>` (the recipe sets it);
- the plugin file inside the installer matches `plugin_sha256`. The store unpacks the installer without running it. If it can't read the installer, this is shown as not checked and doesn't block.

A package that passes is **staged**. The store owner downloads it, tests it, then publishes it. Only then do customers get it and does the update check (1.8) announce it.

## 2. Plugin side (every plugin)

What every plugin must do. How it's built inside the plugin is up to its developer.

### 2.1 Checking a licence
- A token is valid only if every rule in 1.2, 1.3 and 1.5 holds, its signature verifies, and its `product` is the plugin's own product ID (1.7).
- Release builds accept only `kid=1`, public key `7a51af6239b6ed75c695f100cde294f9745a06bad932ed870236dbf4e6578b78`. Test and debug builds may also accept `kid=0` (1.5).
- A licence that can't be read or checked counts as no licence. It never crashes or blocks the plugin or the DAW.

### 2.2 Licensed and not licensed
- The plugin checks the stored licence (1.4) when it loads, and again after a paste. A valid paste takes effect at once, without restarting the DAW, in every open instance of the plugin.
- **Licensed:** the plugin works normally.
- **Not licensed:** the plugin plays no notes and shows the "Not registered" window (2.3).

### 2.3 What the customer sees
- **"Not registered" window**, with two buttons:
  - **Buy**: opens the plugin's shop page (1.7) in the browser;
  - **Paste license**: takes the text on the clipboard, checks it (2.1) and, if valid, stores it (1.4). Shows "Licensed to <name>" or "That license is not valid".
- **About window:**
  - `LICENSED TO <name> (<email>)` from the licence, with `DEV` for `kind=dev` and `NFR` for `kind=nfr`;
  - a **Paste license** button, to replace the key;
  - the **Check for updates** checkbox and the update line (1.8).
- **Update available** badge on the main screen (1.8).

### 2.4 Installer
Built with the store's installer recipe (its `README.md`), not a separate installer. It installs the `.vst3` and copies the key from `license.txt` (1.4). The developer sends the store owner the release package (1.9).

### 2.5 Acceptance tests
- T1–T7 and the reject cases in 1.6 give the stated results. The vectors are for product `testplugin`, so test with that as the expected product.
- A release build rejects `kid=0` tokens.
- A token stored through Paste license is read back from the registry (1.4) and accepted.
- The update check sends the fields in 1.8 and handles every reply listed there.

### 2.6 Developer licences
Developers test with a `kind=dev` licence from the store owner, pasted like a customer would. No bypasses: no force-registered switches, hidden keys or machine checks.

## 3. Backend side (Go server, `/var/www/rogue-syntax/backend`)

Follow `backend/CLAUDE.md`: all server code goes in `doormanapp.go` (the deploy builds only that file), SQL goes through stored procedures, errors through `writeErr`/`opsEmit`.

### 3.1 Production key (one time, offline)
- Generate an Ed25519 keypair with `ed25519.GenerateKey(rand.Reader)`. This is `kid=1`.
- **Private key (seed, 32 bytes):**
  - store it hex-encoded in `/etc/rogue-syntax/license_signing_key` (`root:doorman 640`, like the other secrets; the owner creates it with sudo) and read it with `readSecret("license_signing_key")`;
  - **never** put it in a repo, a log, an error message or an API response;
  - keep one offline backup, for example in a password manager.
- **Public key (32 bytes, hex):** give it to the plugin side for its `kid=1` entry. It is not secret.

### 3.2 Issuing (on a completed purchase)
**Built 2026-11-20** (`doormanapp.go`, section "Licences v1"; schema `backend/sql/licence_schema.sql`; setup `~/doorman-backups/2026-11-20-licensing/step-licensing.sh`).

1. The store already writes one licence row per item bought (`cart.user_licences`, in `processPaymentSuccess`'s transaction). Tokens go in `cart.licence_tokens`, one row per licence: `lid` (the product's prefix + the zero-padded licence ID, e.g. `TEST-000123`), `product`, `kind`, `kid`, `issued`, the token, `revoked`.
   - **A token is made the first time it's needed** (receipt email, download, licence list) by `licenceTokenFor`, then stored and reused, never re-signed. The payment webhook is unchanged, so a missing signing key can't block an order. `issued` is the payment date, so the token doesn't depend on when it was first asked for.
   - **A product opts in** with `"LicenceProduct"` (payload product id) and `"LicencePrefix"` in its product detail JSON (`step-licensing.sh enable <prod_no> <product> <prefix>`). Until then its download is the old one.
   - `name` comes from `user.u_name` (required at sign-up since 2026-11-20; an account without one gets its email as the name). `email` from `user.email`.
2. Build the payload exactly as in 1.2: fixed key order, LF line endings, trailing LF, values stripped of CR, LF and control characters, size limits enforced.
3. Sign the payload with `ed25519.Sign(priv, payloadBytes)` and build the token as in 1.3.
4. Delivery:
   - **Receipt email:** a "Your licence key" box per licence: "the installer adds it for you; if <plugin> says Not registered, click Paste license and paste this key".
   - **Download zip:** the one installer, the readme, and `license.txt` (the token on a line of its own, unwrapped, starting `RS1.`, plus instructions).
   - **Licence list** (`route_getUserLicences`): each licence has `Lid` and `Token`, for the "My plugins" page's copy button (page not built yet).

```go
func makeToken(priv ed25519.PrivateKey, payload []byte) string {
	b := base64.RawURLEncoding
	return "RS1." + b.EncodeToString(payload) + "." + b.EncodeToString(ed25519.Sign(priv, payload))
}
```

### 3.3 Re-sending and lookup
- **Re-send:** the receipt page's Resend sends the receipt email again, with the *stored* tokens. Not built: a separate "email me my licence keys" action.
- **Admin tooling (built):** the operator dashboard's "Issue a licence" panel (`route_opsIssueLicence`, operator only) adds a `dev`, `nfr` or `full` licence to an account by email and shows its key. The owner's own `dev` license is issued this way.

### 3.4 Revocation (v1: records only)
- **v1:** the plugin works offline, so v1 doesn't check revocation. Marking a license `revoked` stops re-sends and gives a list of bad `lid`s.
- **Later:** that list can be compiled into a plugin update. This is a possible v2 change and needs no format change.

### 3.5 Tests
- Using the TEST seed from 1.5, the backend's `makeToken` and payload builder must reproduce T1, T2 and T3 **byte for byte** from the same fields.
- Verify that T4, T5 and T6 fail or are rejected.

### 3.6 What goes away
- **Old keys:** stop issuing the shared bcrypt `RSRegKey` value.
- **Binary injection:** stop patching or injecting anything into plugin binaries or installers.
  - Every customer downloads the same installer. For products not switched over yet, `route_getPurchasedDl` still runs the old flow: it patches a random key into a copy of the plugin (`/var/www/bash/patch_strings_in_file.sh`) and adds an `RSRegKey.Reg` file. Switched products skip all of that. Remove the old flow once every product is switched.
  - The installer writes no registration data of its own: it only copies the token from the customer's `license.txt` (1.4). Paste license is the fallback.

## 4. Decisions for the owner
1. **Existing customers:** none (all accounts so far are tests), so no old keys are carried over.
2. **Unregistered behaviour:** decided 2026-11-20: no notes, and the "Not registered" window with Buy and Paste license (2.2, 2.3). A demo mode can come later.
3. **Machine limits or online activation:** not part of v1. They can be added in v2 with an extra payload key (for example `machine=`). Plugins that ignore unknown keys won't break.
