# Licensing v1: signed license tokens

**Status (2026-11-19):** built on both sides.
- **Store:** built and tested against the shared vectors. Its spec, `docs/licensing-v1.md` in the store repo, is the master copy. This file is the plugin's copy, updated with the store's changes: the `RS1.` prefix, `product` per plugin, a registry subkey per plugin, the production `kid=1` key, and name length.
- **Plugin:** `source/license.h/.cpp`; tests in `tests/license` (all vectors pass).

**Audience:** the agent working on the plugin (this repo) and the agent working on the backend server (separate repo, Go). Section 1 is the shared contract and both sides must follow it exactly. Section 2 covers the plugin, Section 3 the backend.

**What it replaced:** before v1, every customer got the same thing. The plugin read `HKCU\Software\Rogue-Syntax\Registrations\DonnaMedina\RSRegKey` and checks it as a bcrypt hash of one fixed password that is hard-coded in the plugin source (`mdaDX10Processor.cpp`, `mdaBaseController.cpp`). Anyone who has the source or the binary can make a valid key. The new scheme uses public-key signatures:

- The **backend** holds a private key and signs one license per customer.
- The **plugin** contains only the public key, so it can check a license but can never create one.
- Every customer gets the **same plugin binary**. Nothing is injected into the binary per customer.

---

## 1. Shared contract (both sides)

### 1.1 Algorithm
Ed25519 (RFC 8032), with a 64-byte signature and a 32-byte public key.

- **Backend:** Go `crypto/ed25519`.
- **Plugin:** Monocypher's Ed25519 (`optional/monocypher-ed25519.c`, SHA-512). Do **not** use Monocypher's default `crypto_eddsa_*`. That variant uses BLAKE2b and will not verify Go's signatures.

### 1.2 Payload
UTF-8 text with one `key=value` per line. Every line, including the last, ends in `\n` (LF only).

- The backend writes the keys in this order. The plugin must not depend on the order.
- Split each line on the **first** `=`, because values may contain `=`.

| key | value | notes |
|---|---|---|
| `v` | `1` | Format version. The plugin rejects any other value. |
| `product` | `donnamedina` | Names the plugin; one token format covers every Rogue-Syntax plugin. IDs are lowercase `[a-z0-9]{1,32}` and never change once a plugin ships. Each plugin accepts only its own ID (exact, case-sensitive match). |
| `kid` | Integer, e.g. `1` | Which signing key signed this license (see 1.5). `0` is the TEST key and is never used in production. |
| `lid` | e.g. `DM-000123` | License ID, unique, generated by the backend. Must match `[A-Za-z0-9-]{1,40}`. |
| `kind` | `full`, `dev` or `nfr` | `full` = customer, `dev` = the developer's own machines, `nfr` = press or demo copy. In v1 all three unlock the plugin. |
| `name` | Buyer's name | Always present: the store requires a name at sign-up, at most 50 characters. Shown in the plugin's About window. The plugin accepts up to 80 bytes and rejects an empty name. The backend strips CR, LF and control characters. |
| `email` | Buyer's email | Shown in the About window. Max 120 bytes, same stripping. |
| `issued` | `YYYY-MM-DD` | Date issued (UTC). |

- The whole payload is at most 1024 bytes.
- The backend may add new keys later. The plugin **ignores keys it does not know**, but they are still covered by the signature.

### 1.3 Token (what the customer receives)
```
RS1.<base64url(payload)>.<base64url(signature)>
```
- **Prefix:** `RS1.`, the same for every Rogue-Syntax plugin. The prefix isn't signed. The plugin rejects anything without it, including the earlier draft prefix `DM1.`.
- **base64url:** RFC 4648 §5 (`-` and `_`), **no padding**.
- **Signature input:** the signature covers the exact payload bytes. Before checking the signature, the plugin reads only `kid` from the decoded bytes, to pick the key. Every other field is trusted only once the signature checks out. Neither side re-serialises the payload before verifying.
- **Pasted tokens:** the plugin removes **all whitespace** (spaces, tabs, CR, LF) before parsing, because email clients wrap long lines. The backend never puts whitespace inside a token.

### 1.4 Where the license lives on the customer's machine
- **Location:** one subkey per plugin, `HKCU\Software\Rogue-Syntax\Registrations\<PluginKey>`, value **`License`**, type `REG_SZ`, holding the token.
  - Donna Mediña uses `...\Registrations\DonnaMedina`, the key the old `RSRegKey` sits under. A new plugin gets its own subkey.
  - HKCU needs no admin rights, so the plugin can write the value itself.
- **Who writes it:** only the plugin, when the user clicks **Paste license** (Section 2). The store no longer ships a `.reg` file.
- **How customers get their token:**
  - in the receipt email;
  - in a `license.txt` inside the download zip;
  - later, on their account page.
  - Each one says "open Donna Mediña and click Paste license", so the button label must stay **Paste license**.

### 1.5 Keys and key IDs
- **`kid=0`, the TEST key.** It is public and is only for these test vectors.
  - Seed: `000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f`
  - Public key: `03a107bff3ce10be1d70dd18e74bc09967e4d6309ba50d5f1ddc8664125531b8`
  - Release builds of the plugin must **not** accept `kid=0`. Debug builds and tests may.
- **`kid=1`, the first production key.** The backend generated it (3.1); only its **public** key is in the plugin. Release builds accept only `kid=1`. Every Rogue-Syntax plugin uses the same key table.
  - Public key: `7a51af6239b6ed75c695f100cde294f9745a06bad932ed870236dbf4e6578b78`
- **Rotation:** the plugin holds a small table `kid -> public key`. Rotating means adding `kid=2` to the table in a plugin update and starting to sign with it. Old licenses keep working for as long as their `kid` stays in the table.

## 2. Plugin side (this repo): as built

### 2.1 Library
- **Monocypher 4.0.2**, vendored in `external/monocypher/` as a flat folder: `monocypher.c/.h`, `monocypher-ed25519.c/.h`, `LICENCE.md`, `VERSION.txt`.
- **Function used:** only `crypto_ed25519_check(sig, pub, msg, len)` (SHA-512), which returns 0 when the signature is valid.
- **Credits:** in `licenses/THIRD-PARTY-NOTICES.txt` and the About window's credits page, under its 2-clause BSD licence (`tools/gen_notices.ps1`).
- **libbcrypt** is no longer compiled or credited. The folder `external/libbcrypt` is kept, but nothing uses it.

### 2.2 `source/license.h/.cpp`
- **`verifyTokenWithKeys(token, keys, n, out)`** checks a token against a given key table and does everything in 1.2 and 1.3. It also rejects:
  - an unknown `kind`, so a future `trial` kind doesn't unlock this version;
  - a repeated key, an empty key, or a control character;
  - a `lid` or `issued` that doesn't match its format;
  - non-zero leftover bits in base64url.
- **`verifyToken(token, out)`** uses the built-in table: `kid=1` in every build, plus the TEST key `kid=0` only under `_DEBUG`.
- **`loadStoredToken()` / `storeToken()`** read and write the registry value in 1.4. Tests pass a scratch subkey.
- **`clipboardText()`** returns the clipboard as UTF-8.
- Nothing throws; every failure returns false.

### 2.3 Wiring
- **Processor:** `DX10Processor::refreshLicense()` sets `regKeyLegit` (`std::atomic<bool>`, read by `noteOn`). It runs in the constructor and on `CMSG_LICENSE_CHANGED_CHAR` ('l').
  - The message carries nothing: the processor re-reads and verifies the stored token itself.
  - The bcrypt check, both hard-coded passwords and the force-registered lines are gone. `constants::isRegLegit` is gone too.
- **Controller:** `BaseController::refreshLicense()` (in `initialize`, and on every editor open) sets its own `licensed` and `licenseInfo`.
  - `pasteLicense()` reads the clipboard, verifies the token, stores it, then calls `notifyLicenseChanged()`.
  - An editor open that finds a license (for example, one pasted in another instance) also notifies its processor.
- **Unlicensed behaviour:** no notes play (as before), and the editor shows the license screen.

### 2.4 UI
- **License screen** (`NVGView::drawBadReg`, layout `editorLayout::licenseScreen`):
  - "No license found", with where to find the license;
  - the **Paste license** button;
  - the result of the last paste ("That license is not valid." and similar);
  - a WWW.ROGUE-SYNTAX.COM link.
  - Clicks go to the invisible custom view `licensePanel` (`LicenseView`, `presetBarView.h`). It is last in `vstgui.uidesc`, so it sits on top, and it is mouse-enabled only while unlicensed. It swallows clicks inside the box.
- **About window:** `LICENSED TO <name>  (<email>)`, followed by `|  DEV` or `|  NFR` for those kinds.
  - If that would run into the build stamp, the email goes first, then the name is cut, on whole UTF-8 characters.
  - Shows `UNLICENSED` otherwise.

### 2.5 Tests
- **`tests\license\build_and_run.bat`** (self-contained, release settings): 46 checks.
  - T1–T7 and the reject list in 1.6;
  - further payloads signed with the TEST key: unknown key ignored, `v=2`, unknown kind, `nfr`, case of `product`, empty name, repeated key, control character, missing trailing LF, missing field, bad `lid` or date, payload size limit, `RS2.`;
  - the release table rejects `kid=0`;
  - store and load through a scratch subkey.
  - `tests/license/vectors.h` is generated from `tools/license/testvectors.go`.
- **Existing suites:** the note_off test sets `regKeyLegit` on its own processor instance, as before, so it doesn't need a license. `editor_cycle` covers the new view.

### 2.6 Developer machine
The owner gets a `kind=dev` license from the store's operator dashboard and pastes it like a customer would. There are no bypasses and no machine-ID checks.

### 2.7 What the store serves
The download serves exactly `/var/www/downloads/1/DonnaMedinaVST64.vst3`. That is the file the post-build step installs as `C:\Program Files\Common Files\VST3\DonnaMedinaVST64.vst3` (built as `x64\Release\RSSynth001donnaMedina.vst3`). If the plugin ever ships as something else, such as an installer `.exe`, the owner must change the store's product settings.

## 3. Backend side (Go server, separate repo)

The store's `docs/licensing-v1.md` is the master copy of this section; what follows is the original brief.

### 3.1 Production key (one time, offline)
- Generate an Ed25519 keypair with `ed25519.GenerateKey(rand.Reader)`. This is `kid=1`.
- **Private key (seed, 32 bytes):**
  - store it in the server's secret store or an environment variable (`DM_LICENSE_SIGNING_KEY`, hex);
  - **never** put it in a repo, a log, an error message or an API response;
  - keep one offline backup, for example in a password manager.
- **Public key (32 bytes, hex):** give it to the plugin side for its `kid=1` entry. It is not secret.

### 3.2 Issuing (on a completed purchase)
1. Create a license record:
   - `lid` (unique, e.g. `DM-` + a zero-padded sequence number), `order_id`, `name`, `email`, `kind`, `issued`, `kid`;
   - `revoked bool` and `created_at`;
   - the token itself.
2. Build the payload exactly as in 1.2: fixed key order, LF line endings, trailing LF, values stripped of CR, LF and control characters, size limits enforced.
3. Sign the payload with `ed25519.Sign(priv, payloadBytes)` and build the token as in 1.3.
4. Email the token, and show it on the customer's account or order page with a copy button.
   - Delivery text: "Open Donna Medina, click Paste license."

```go
func makeToken(priv ed25519.PrivateKey, payload []byte) string {
	b := base64.RawURLEncoding
	return "RS1." + b.EncodeToString(payload) + "." + b.EncodeToString(ed25519.Sign(priv, payload))
}
```

### 3.3 Re-sending and lookup
- **Re-send:** an endpoint or admin action that re-sends the *stored* token. Don't re-sign; the existing token stays valid.
- **Admin tooling:** issue a `dev` or `nfr` license by hand. The owner's own `dev` license is issued this way.

### 3.4 Revocation (v1: records only)
- **v1:** the plugin works offline, so v1 doesn't check revocation. Marking a license `revoked` stops re-sends and gives a list of bad `lid`s.
- **Later:** that list can be compiled into a plugin update. This is a possible v2 change and needs no format change.

### 3.5 Tests
- Using the TEST seed from 1.5, the backend's `makeToken` and payload builder must reproduce T1, T2 and T3 **byte for byte** from the same fields.
- Verify that T4, T5 and T6 fail or are rejected.

### 3.6 What goes away
- **Old keys:** stop issuing the shared bcrypt `RSRegKey` value.
- **Binary injection:** stop patching or injecting anything into plugin binaries or installers.
  - Every customer downloads the same installer.
  - The installer no longer writes registration data. The customer pastes the token.

## 4. Decisions for the owner
1. **Existing customers:** the plugin no longer accepts the old `RSRegKey` (its password is in the source and git history, so old keys can be forged). Existing customers need a v1 token; the recommended route is a one-off store job that issues one for every existing order and emails it.
2. **Unregistered behaviour:** keep "no notes" (as now), or move to a demo mode, such as full sound with a periodic short dropout or no preset saving.
3. **Machine limits or online activation:** not part of v1. They can be added in v2 with an extra payload key (for example `machine=`). Plugins that ignore unknown keys won't break.
