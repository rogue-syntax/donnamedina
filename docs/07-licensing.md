# Licensing v1: signed license tokens

**Status:** spec, not built yet (2026-11-19).

**Audience:** the agent working on the plugin (this repo) and the agent working on the backend server (separate repo, Go). Section 1 is the shared contract and both sides must follow it exactly. Section 2 covers the plugin, Section 3 the backend.

**What it replaces:** today every customer gets the same thing. The plugin reads `HKCU\Software\Rogue-Syntax\Registrations\DonnaMedina\RSRegKey` and checks it as a bcrypt hash of one fixed password that is hard-coded in the plugin source (`mdaDX10Processor.cpp`, `mdaBaseController.cpp`). Anyone who has the source or the binary can make a valid key. The new scheme uses public-key signatures:

- The **backend** holds a private key and signs one license per customer.
- The **plugin** contains only the public key, so it can check a license but can never create one.
- Every customer gets the **same plugin binary**. Nothing is injected into the binary per customer.

---

## 1. Shared contract (both sides)

### 1.1 Algorithm
Ed25519 (RFC 8032), with a 64-byte signature and a 32-byte public key.

- **Backend:** Go `crypto/ed25519`.
- **Plugin:** Monocypher's Ed25519 (`optional/monocypher-ed25519.c`, SHA-512). Do **not** use Monocypher's default `crypto_eddsa_*`. That variant uses BLAKE2b and will not verify Go's signatures.

### 1.2 Payload
UTF-8 text with one `key=value` per line. Every line, including the last, ends in `\n` (LF only).

- The backend writes the keys in this order. The plugin must not depend on the order.
- Split each line on the **first** `=`, because values may contain `=`.

| key | value | notes |
|---|---|---|
| `v` | `1` | Format version. The plugin rejects any other value. |
| `product` | `donnamedina` | The plugin rejects any other value. |
| `kid` | Integer, e.g. `1` | Which signing key signed this license (see 1.5). `0` is the TEST key and is never used in production. |
| `lid` | e.g. `DM-000123` | License ID, unique, generated by the backend. Must match `[A-Za-z0-9-]{1,40}`. |
| `kind` | `full`, `dev` or `nfr` | `full` = customer, `dev` = the developer's own machines, `nfr` = press or demo copy. In v1 all three unlock the plugin. |
| `name` | Buyer's name | Shown in the plugin's About window. Max 80 bytes. The backend strips CR, LF and control characters. |
| `email` | Buyer's email | Shown in the About window. Max 120 bytes, same stripping. |
| `issued` | `YYYY-MM-DD` | Date issued (UTC). |

- The whole payload is at most 1024 bytes.
- The backend may add new keys later. The plugin **ignores keys it does not know**, but they are still covered by the signature.

### 1.3 Token (what the customer receives)
```
DM1.<base64url(payload)>.<base64url(signature)>
```
- **base64url:** RFC 4648 §5 (`-` and `_`), **no padding**.
- **Signature input:** the signature covers the exact payload bytes. The plugin verifies the decoded bytes first and only then parses them. Neither side re-serialises the payload before verifying.
- **Pasted tokens:** the plugin removes **all whitespace** (spaces, tabs, CR, LF) before parsing, because email clients wrap long lines. The backend never puts whitespace inside a token.

### 1.4 Where the license lives on the customer's machine
- **Location:** registry value `HKCU\Software\Rogue-Syntax\Registrations\DonnaMedina`, name **`License`**, type `REG_SZ`, holding the token.
  - This is the same key the old `RSRegKey` sits under. HKCU needs no admin rights, so the plugin can write the value itself.
- **Who writes it:**
  - the plugin, when the user pastes a token (Section 2);
  - optionally the installer, if the backend ever produces per-customer installers. It must not do this in v1 (see 3.6).

### 1.5 Keys and key IDs
- **`kid=0`, the TEST key.** It is public and is only for these test vectors.
  - Seed: `000102030405060708090a0b0c0d0e0f101112131415161718191a1b1c1d1e1f`
  - Public key: `03a107bff3ce10be1d70dd18e74bc09967e4d6309ba50d5f1ddc8664125531b8`
  - Release builds of the plugin must **not** accept `kid=0`. Debug builds and tests may.
- **`kid=1`, the first production key.** The backend generates it (3.1). Only its **public** key is given to the plugin side.
- **Rotation:** the plugin holds a small table `kid -> public key`. Rotating means adding `kid=2` to the table in a plugin update and starting to sign with it. Old licenses keep working for as long as their `kid` stays in the table.

## 2. Plugin side (this repo)

### 2.1 Library
- Vendor **Monocypher 4.x** into `external/monocypher/`. Four files are needed: `monocypher.c/.h` and `optional/monocypher-ed25519.c/.h`.
- The verify call is `crypto_ed25519_check(sig, pub, msg, len)` and returns 0 when the signature is valid. Confirm the exact signature in the vendored header.
- Use relative include paths only.
- Monocypher is BSD-2-Clause / CC0. Add it to `licenses/THIRD-PARTY-NOTICES.txt` and regenerate `source/creditsText.h` with `tools/gen_notices.ps1`.

### 2.2 New module `source/license.h/.cpp`
- `bool verifyToken(const std::string& token, License& out)`. It does everything in 1.3 and 1.2: strip whitespace, split, base64url-decode, check the `kid` table, verify the signature, parse the payload and check the fields. It fills `out` with `lid`, `kind`, `name`, `email` and `issued`.
- `std::string loadStoredToken()` and `bool storeToken(const std::string&)`, using the registry value in 1.4. `regReader.h` already reads HKCU, despite its function being named `...FromHKLM`.
- Key table: `kid=1` with its production public key. `kid=0` (TEST) is included only under `#ifdef _DEBUG` or in test builds.
- Must not throw. Every failure returns false.

### 2.3 Wiring
- **Processor** (`DX10Processor::initialize`):
  - load the stored token, verify it, and set `regKeyLegit` from the result;
  - remove the old bcrypt check, the hard-coded password and the `TESTING ONLY - FORCE REGISTERED` lines.
- **Controller:**
  - verifies the token independently for the UI, to show the state and the licensee's name;
  - doesn't trust a flag set by the processor.
- **Processor and controller agreeing:**
  - after the user pastes a valid token, the controller stores it and sends the processor a message (`IMessage`, id `"licenseChanged"`);
  - the processor then re-reads the token from the registry and verifies it again. The message carries no token and no flag.
- **Replace `constants::isRegLegit`.** It is a process-wide static shared between instances. Replace it with per-instance state on each side.
- **Unregistered behaviour:** keep what it does today (`noteOn` does nothing; the editor shows the "No registration detected" screen). The owner may change this later.

### 2.4 UI
- **Registration screen (`NVGView.cpp`, around line 2528):**
  - add a **"Paste license"** button. It reads the clipboard text (`CF_UNICODETEXT`, converted to UTF-8), verifies it, and stores it if it's valid;
  - show a short result: "Licensed to <name>" or "That license is not valid".
  - keep the link to rogue-syntax.com.
- **About window (`NVGView.cpp`, around line 4266):** `REGISTERED` becomes `LICENSED TO <name> (<email>)`.
  - For `kind=dev`, append `DEV`; for `kind=nfr`, append `NFR`.

### 2.5 Tests (`tests/note_off` or a new `tests/license`)
- All vectors T1–T7 and the extra reject cases in 1.6.
- Store, then load, through the registry. Use a test subkey, not the real one.
- The release key table rejects `kid=0`.
- Build check as usual (CLAUDE.md). Log any SDK change in `docs/05-sdk-mods.md`; none is expected.

### 2.6 Developer machine
The owner gets a `kind=dev` license from the backend and pastes it like a customer would. The uncommitted force-registered lines are then gone for good. Don't add machine-ID checks or other bypasses.

## 3. Backend side (Go server, separate repo)

### 3.1 Production key (one time, offline)
- Generate an Ed25519 keypair with `ed25519.GenerateKey(rand.Reader)`. This is `kid=1`.
- **Private key (seed, 32 bytes):**
  - store it in the server's secret store or an environment variable (`DM_LICENSE_SIGNING_KEY`, hex);
  - **never** put it in a repo, a log, an error message or an API response;
  - keep one offline backup, for example in a password manager.
- **Public key (32 bytes, hex):** give it to the plugin side for its `kid=1` entry. It is not secret.

### 3.2 Issuing (on a completed purchase)
1. Create a license record:
   - `lid` (unique, e.g. `DM-` + a zero-padded sequence number), `order_id`, `name`, `email`, `kind`, `issued`, `kid`;
   - `revoked bool` and `created_at`;
   - the token itself.
2. Build the payload exactly as in 1.2: fixed key order, LF line endings, trailing LF, values stripped of CR, LF and control characters, size limits enforced.
3. Sign the payload with `ed25519.Sign(priv, payloadBytes)` and build the token as in 1.3.
4. Email the token, and show it on the customer's account or order page with a copy button.
   - Delivery text: "Open Donna Medina, click Paste license."

```go
func makeToken(priv ed25519.PrivateKey, payload []byte) string {
	b := base64.RawURLEncoding
	return "DM1." + b.EncodeToString(payload) + "." + b.EncodeToString(ed25519.Sign(priv, payload))
}
```

### 3.3 Re-sending and lookup
- **Re-send:** an endpoint or admin action that re-sends the *stored* token. Don't re-sign; the existing token stays valid.
- **Admin tooling:** issue a `dev` or `nfr` license by hand. The owner's own `dev` license is issued this way.

### 3.4 Revocation (v1: records only)
- **v1:** the plugin works offline, so v1 doesn't check revocation. Marking a license `revoked` stops re-sends and gives a list of bad `lid`s.
- **Later:** that list can be compiled into a plugin update. This is a possible v2 change and needs no format change.

### 3.5 Tests
- Using the TEST seed from 1.5, the backend's `makeToken` and payload builder must reproduce T1, T2 and T3 **byte for byte** from the same fields.
- Verify that T4, T5 and T6 fail or are rejected.

### 3.6 What goes away
- **Old keys:** stop issuing the shared bcrypt `RSRegKey` value.
- **Binary injection:** stop patching or injecting anything into plugin binaries or installers.
  - Every customer downloads the same installer.
  - The installer no longer writes registration data. The customer pastes the token.

## 4. Decisions for the owner
1. **Existing customers:** recommended is a one-off backend job that issues a v1 token for every existing order and emails it.
   - The alternative is for the plugin to keep accepting the old `RSRegKey`. That isn't recommended: the old password is in the source and git history, so old keys can be forged.
2. **Unregistered behaviour:** keep "no notes" (as now), or move to a demo mode, such as full sound with a periodic short dropout or no preset saving.
3. **Machine limits or online activation:** not part of v1. They can be added in v2 with an extra payload key (for example `machine=`). Plugins that ignore unknown keys won't break.
